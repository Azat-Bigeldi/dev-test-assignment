- **Дневной лимит.** Сутки — календарная дата `createdAt` по UTC+5 (`src/day.ts`). Если выбранный филиал заполнен, берётся ближайший незаполненный филиал магазина с правилом `geo`, иначе `unassigned`. `manual` лимит не проверяет.
- **API** (`src/app.ts`, `src/dispatcher.ts`): `POST /orders/:id/assign` и `GET /branches/:id/load?date=`. Обработчик вынесен из `server.ts`, чтобы тесты поднимали его на случайном порту.
- **Тесты:** закрыты все `test.todo`, добавлены тесты на граничные случаи лимита, даты по Алматы и HTTP API на данных из `data/`.

### Допущения

- `manual`-заказ тоже занимает место в лимите филиала: лимит он не проверяет, но филиал его всё равно собирает. Поэтому после ручного заказа филиал может оказаться заполнен сверх лимита.
- Повторный `assign` возвращает сохранённый результат, включая `unassigned`. Данные заказов не меняются, а лимит только заполняется, так что повторный расчёт дал бы тот же ответ.
- Запасной филиал при заполненном выбранном — ближайший незаполненный среди **всех** активных филиалов магазина, без приоритета города (так написано в условии). Без координат заказа запасной не выбрать, и заказ получает `unassigned`.
- Если пункт выдачи закреплён за неактивным филиалом, правило `pickup_point` не срабатывает, и проверяются следующие правила.
- Некорректная дата в `GET /branches/:id/load` — всё, что не является реальной датой `YYYY-MM-DD` (например, `2026-02-30`). Дата проверяется раньше, чем существование филиала.

### Несколько экземпляров с общей БД

Сейчас распределения и счётчики загрузки лежат в памяти процесса, и их корректность держится на том, что Node однопоточен: между проверкой лимита и записью нет `await`. С несколькими экземплярами:

- **Состояние переезжает в БД:** таблица распределений и счётчик `branch_id + date → assigned`. Иначе у каждого экземпляра свой лимит и своя история повторов.
- **Гонка за лимит.** Два экземпляра одновременно видят `assigned = 2 < 3` и оба берут место. Место нужно занимать атомарно: `UPDATE branch_load SET assigned = assigned + 1 WHERE branch_id = $1 AND date = $2 AND assigned < $limit` и проверять число изменённых строк. Если 0, филиал заполнен, и пробуется следующий кандидат. Другой вариант — транзакция с `SELECT … FOR UPDATE` на строке счётчика.
- **Идемпотентность.** Дубль запроса может прийти на другой экземпляр одновременно с первым. Нужен уникальный ключ по `order_id` в таблице распределений, и вставка распределения с увеличением счётчика в одной транзакции. Проигравший дубль ловит конфликт и возвращает уже сохранённое распределение.
- **Справочник филиалов** (активность, лимиты, пункты выдачи) читается из БД, а не из файла при старте, чтобы изменения сразу видели все экземпляры.

## Задача 2. Онлайн-запись

### Что сделано

- **Баг.** `overlaps` сравнивал через `<=`, поэтому интервалы `10:00–11:00` и `11:00–12:00` считались пересекающимися. Интервалы теперь полуоткрытые `[start, end)`: `a.start < b.end && b.start < a.end`.
- **Слоты** (`src/slots.ts`): `getSlots` принимает текущий момент параметром (`now`) и остаётся чистой функцией. Перерывы сравниваются в местных минутах дня, а записи в абсолютном времени (мс UTC), поэтому часовой пояс и записи на стыке суток считаются корректно. Слот, который начинается ровно сейчас, уже не выдаётся («позже текущего момента»).
- **Создание записи** (`src/booking.ts`): `start` должен быть ISO-строкой с `Z` или `±hh:mm`. Время переводится в Алматы, и запись создаётся, только если это время есть в `getSlots`. Слот проверяется той же функцией, что отдаёт `GET …/slots`, поэтому правила не расходятся. Время не на 15-минутной сетке, с секундами, в прошлом или в выходной даёт `409 slot_unavailable`.
- **Одновременные бронирования.** `listByMaster` и `insert` работают с задержкой, поэтому без защиты два запроса оба видят слот свободным и оба вставляют запись. Проверка и вставка идут под замком мастера (`src/lock.ts`, очередь промисов по ключу). Ключ — мастер, а не слот, потому что пересекаться могут разные услуги с разным началом (стрижка 15:00 и брови 15:30). Тесты отправляют 10 одновременных запросов на одно время и пару пересекающихся записей разных услуг. Я проверил, что без замка оба теста падают.
- **Телефон** (`src/phone.ts`): разрешены цифры, пробелы, `-`, `()` и `+` в начале. Префикс `+7`, `8` или `7`, всего 11 цифр. Код оператора проверяется по списку мобильных кодов Казахстана (700–708, 747, 750–751, 760–764, 771, 775–778), поэтому городской `+7 727…` и российский `+7 916…` не проходят.
- **Отмена:** `too_late`, если до начала меньше 2 часов, включая уже начавшиеся и прошедшие записи. Ровно за 2 часа отменить можно. Повторная отмена возвращает `200` без проверки времени.
- **API** (`src/app.ts`): обработчик вынесен из `server.ts`, как в задаче 1. Репозиторий создаётся фабрикой `createBookingRepo` (задержка осталась), чтобы у каждого теста было своё состояние. `now` по умолчанию берётся из `clock.ts`, в тестах подставляется своё.
- **Тесты:** закрыты все `test.todo`, добавлены тесты на нормализацию телефона, HTTP API (слоты, создание, валидация, гонки, отмена) и граничные случаи времени.

### Допущения

- Порядок проверок в `GET …/slots`: сначала параметры и дата (`400`), потом мастер и услуга (`404`), потом «мастер не оказывает услугу» (`400`). В `POST /bookings` так же: неизвестный мастер или услуга дают `404`, этого в условии нет.
- Номер без кода страны (`7012345678`) не принимается: десять цифр легко спутать с опечаткой.
- `id` новой записи — `bk-<uuid>`.
- Замок держится в памяти процесса и защищает только один экземпляр, об этом ниже.

### Что есть в исходнике README, но не в условии

В `task-2-booking/README.md` есть HTML-комментарий (на GitHub он не виден) про технический перерыв 7 минут после каждой записи. Это одна строка, и тогда понятно, нужен ли буфер перед перерывом и концом дня.

### Несколько экземпляров с PostgreSQL

Замок в памяти перестаёт работать, как только экземпляров больше одного. Гарантию должна давать база:

- **Основной вариант — exclusion constraint.** Пересечение записей мастера запрещается на уровне схемы:
  ```sql
  CREATE EXTENSION btree_gist;
  ALTER TABLE bookings ADD CONSTRAINT bookings_no_overlap
    EXCLUDE USING gist (master_id WITH =, tstzrange(start_at, end_at, '[)') WITH &&)
    WHERE (status = 'active');
  ```
  Приложение по-прежнему проверяет слот (график, перерывы, прошлое), а потом делает `INSERT`. Если параллельный запрос успел раньше, PostgreSQL вернёт `23P01 exclusion_violation`, и мы отвечаем `409 slot_unavailable`. Это работает с любым числом экземпляров, не требует блокировок в коде и закрывает пересечения разных услуг. Диапазон `[)` совпадает с полуоткрытыми интервалами в `overlaps`, а условие `WHERE status = 'active'` позволяет занять время отменённой записи.
- **Альтернатива — сериализация по мастеру:** в транзакции `SELECT … FROM masters WHERE id = $1 FOR UPDATE` или `pg_advisory_xact_lock(hashtext(master_id))`, затем чтение записей, проверка и вставка. Так повторяется текущий замок, но в базе. Минус в том, что инвариант держится на дисциплине кода: любой путь вставки без блокировки его ломает. Поэтому constraint я бы оставил в любом случае.
- `SERIALIZABLE` тоже сработает, но тогда нужен повтор транзакции при `40001`, а ошибки сериализации возможны и на несвязанных записях.
- **Отмена** — одним `UPDATE bookings SET status = 'cancelled' WHERE id = $1 AND (status = 'cancelled' OR start_at - now() >= interval '2 hours') RETURNING *`, чтобы проверка времени и изменение были атомарными. Текущее время берётся из приложения (`clock.ts`), а не из `now()` базы, если важна подмена `NOW`.
- Повторные `POST` от клиента (ретраи после таймаута) стоит дедуплицировать заголовком `Idempotency-Key` с уникальным индексом. Иначе клиент получит `409` на собственную же запись.
